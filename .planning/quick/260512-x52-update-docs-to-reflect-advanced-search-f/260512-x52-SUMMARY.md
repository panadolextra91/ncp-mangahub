## Decisions Made

### Decision 1 — Task 3 (ARCHITECTURE.md) proceeded rather than skipped

The plan flagged Task 3 as optional. I proceeded because:

1. The existing ARCHITECTURE.md describes HTTP and gRPC as separate adapters (which they are), but never points out **where they converge** in the application layer. After wh7, both adapters route through `application.MangaService.SearchMangasWithFilters` for the shared filter surface — that is a non-obvious cross-cutting fact a future maintainer needs in order to safely add a new filter type.
2. The note is genuinely additive: 10 new lines, appended after the existing Tech Stack section under a horizontal rule, with no edits to any existing sentence, diagram, or bullet. ARCHITECTURE.md's voice (Vietnamese prose + English code terms) is preserved.
3. The contract pointer (`xem API_CONTRACT.md §2.2`) keeps the architecture doc lean — readers who want full SQL / param semantics follow the link rather than duplicating content.

### Decision 2 — README-eng.md: preserve "100+ Manga Titles" as a new "Pre-seeded Catalog" bullet

The plan gave the executor a choice: keep the fact as its own bullet OR fold it into Personal Library. I kept it as a standalone bullet (`🌱 Pre-seeded Catalog`) because:

- Personal Library is a runtime feature (user actions on the shelf), the 100+ titles is a build-time seed fact — conflating them dilutes both.
- An idiomatic English bullet noun ("Pre-seeded Catalog") makes the seed-data fact discoverable on a quick skim.

### Decision 3 — Placement of the Advanced Search bullet in README.md

The plan offered two acceptable slots ("between RBAC and Personal Library" OR "between Web Scraping and Graceful Shutdown"). I chose the latter (after Web Scraping, before Graceful Shutdown) because it groups all data-feature bullets (Personal Library, Web Scraping, Advanced Search) consecutively before the runtime/operational bullet (Graceful Shutdown). The README's feature list now reads top-to-bottom as: surface → identity → data features → operational concerns.

### Decision 4 — §6 Web Scraping numbered, not embedded in §5

The plan said "After §5 (or before the Summary Table), add a new top-level section `## 🕸️ 6. Web Scraping (Internal Service)`." I followed the literal spec and made it a top-level section numbered `6`, with the scraper itself nested as `### 6.1 Quote-of-the-day Scraper`. This matches the numbering style of other top-level sections (§1–§5).

## Surprises & Notes from Canonical Source Reads

1. **The original dangling §5.1 fragment was even worse than the plan implied.** The pre-x52 file ended `### 5.1 Update Reading Progress` with the Mermaid block, then dropped straight into 3 orphan SQL lines (`status = excluded.status, / updated_at = CURRENT_TIMESTAMP; / ` ``` `) — there was no `**SQL Query**:` label and no opening `INSERT`. A reader scrolling through would have seen a fenced code block with no opening statement and no header. The fix restores both the label and the full UPSERT.

2. **The summary-table row for Web Scraping said "HTTP (External)".** This was technically not wrong (the scraper does make an outbound HTTP GET) but it was actively misleading because the column it sits in describes the *protocol of the service surface*, and every other row in that column describes the protocol clients use to reach the service. A reader scanning the table would conclude there is a public `GET /api/scrape` or similar — there is not. Changed to `Internal (TUI-invoked)` for clarity.

3. **`SearchWithFilters` already has its own defensive 10-genre cap** in the repo layer, in addition to the cap in the HTTP handler. This is genuine belt-and-suspenders defense-in-depth (a future gRPC client bypassing the handler still cannot run a 1000-genre query). The contract documents the cap at the user-facing layer (10 genres per request) and treats the repo cap as an internal safety net (not over-promised in the doc).

4. **`SearchRequest` proto field numbers are stable.** `query=1` was the existing field; `genres=2`, `status=3`, `sort_by=4` were added without renumbering. This means clients compiled against the pre-wh7 proto still work — they simply omit the new fields, which the server treats as "no filter" (correctly routed through legacy `SearchMangas`). The contract calls this out explicitly so future proto edits don't silently break wire-level compat.

5. **CLI does NOT yet pass `genres`/`status`/`sortBy`.** `internal/interfaces/cli/manga.go` `manga search [query]` still calls only `GET /api/manga?q=...`. The contract doc does not pretend the CLI supports filters — it only documents the HTTP and gRPC surfaces. Future quick task could enhance the CLI; not in scope for x52.
